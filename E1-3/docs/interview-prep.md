## Q1. data.json에 새 라벨 `'o'`가 추가되면, 어떤 순서로 확장하나?

### 답변 뼈대

**핵심: 확장 순서는 "데이터가 들어오는 지점부터 나가는 지점 순서"다.**

```
1) normalize_label 의 매핑에 'o' → 'O' (또는 정한 표준 라벨) 한 줄 추가
   → LABEL_MAP = {"+": "Cross", "x": "X", "o": "O", ...}

2) decide() 확장 — 지금은 2개 점수만 비교하는데 3개(Cross/X/O)를 비교해야 함
   → 가장 높은 점수를 찾고, 최고점이 2개 이상이면 UNDECIDED
   → max(), 또는 점수들을 정렬해서 1등과 2등의 차이가 epsilon 이하인지 확인

3) 필터 로딩 부분 — size_N 딕셔너리에 'o' 필터도 함께 읽어오도록 확장
   (filters[size_N] 안에 'o' 키가 있다고 가정)

4) 출력 함수(print_case_result) — 지금 "Cross 점수 / X 점수" 두 줄인데
   "O 점수" 한 줄 추가. 하드코딩하지 않고 라벨 목록을 반복문으로 돌면
   라벨이 몇 개든 자동으로 대응됨

5) 테스트 — 'o' 패턴이 포함된 케이스를 넣어 정상적으로 O로 판정되는지,
   Cross/X/O 세 개가 모두 근접한 삼중 동점일 때도 UNDECIDED가 되는지 확인
```

### 한 문장 요약

**"입구(라벨 매핑) → 중간(점수 비교 로직) → 출구(출력) → 검증(테스트) 순서로, 하드코딩된 2개 비교를 N개 비교로 일반화하면 됩니다."**

### 설계와 연결

지금 `normalize_label`을 딕셔너리로, `print_case_result`를 반복문 기반으로 짜두면 이 확장이 실제로 "한 줄 추가" 수준이 된다. **지금 설계 방식 자체가 이 질문에 대한 답의 근거**가 된다.

## Q2. 1000×1000 패턴이면 시간/메모리 문제와 최적화 우선순위는?

### 계산으로 감을 잡기

```
25×25   =    625 회 연산   (지금 최대 크기)
1000×1000 = 1,000,000 회 연산

1,000,000 / 625 = 1,600배
```

25×25도 몇 ms 안 걸렸으니 1000×1000은 "느려서 못 쓸 정도"는 아니다. 하지만:

### 시간 문제

- 지금 구현은 **순수 파이썬 이중 for문**이다. 파이썬 반복문은 C로 짠 것보다 훨씬 느리다(보통 수십~수백 배).
- 필터가 여러 개(Cross, X, O, ...)면 **필터 개수만큼 곱해서** 느려진다.
- 실무에서는 이 지점에서 NumPy 벡터화나 GPU/NPU 병렬 처리로 넘어간다.

### 메모리 문제

- 2차원 리스트로 저장하면 파이썬 객체 오버헤드가 커서, 1000×1000짜리 리스트 하나가 생각보다 메모리를 많이 먹는다.
- **보너스 C1(1차원 배열 변환)이 정확히 이 문제의 완화책이다** — 1차원 배열은 메모리 접근이 더 규칙적이고 오버헤드가 적다.

### 우선순위

1. **1차원 배열 변환부터** (이미 구현한 보너스 C1) — 코드 구조를 크게 안 바꿔도 됨
2. 그다음 반복 자체를 줄이는 알고리즘적 최적화(예: 필터가 0인 위치는 곱셈 생략)
3. 그래도 부족하면 NumPy/병렬화 — 이건 "외부 라이브러리 금지" 제약이 풀렸을 때 이야기

### 한 문장 요약

**"연산 횟수가 1600배로 늘어나므로 시간이 문제가 되고, 파이썬 리스트의 메모리 오버헤드도 문제가 됩니다. 구조를 크게 안 바꾸는 1차원 배열 변환을 먼저 적용하고, 그래도 부족하면 알고리즘 최적화나 병렬화를 고려하겠습니다."**

## Q3. CPU 직렬 처리 vs NPU 병렬 처리 — 병목은 어디에?

### CPU의 병목

CPU는 "명령어를 하나씩 순서대로" 처리하도록 설계됐다. MAC 연산 625번을 하려면 **625번의 곱셈+덧셈을 한 줄씩** 실행해야 한다. 코어가 여러 개 있어도, 우리 코드(이중 for문)는 **그 병렬성을 전혀 안 쓰고 있다** — 그냥 한 줄씩 순서대로 도는 코드이기 때문이다.

→ **병목은 "명령어 하나하나가 순차적으로만 실행된다"는 점.**

### NPU의 해법

NPU는 애초에 **"곱하고 더하기"라는 단순 연산을 수천 개 동시에** 처리하도록 회로 자체가 설계되어 있다. 625번의 곱셈을 순서대로 하는 게 아니라, **한 번에 왕창** 처리한다.

### 이 과제 코드와 연결

우리가 짠 이중 for문은 **정확히 CPU의 직렬 처리 방식**이다. 만약 이 루프를 "각 칸의 곱셈을 동시에 계산하는 하드웨어"에 통째로 던질 수 있다면, 이론적으로 **연산 시간이 N²가 아니라 거의 O(1)**에 가까워진다(회로가 모든 칸을 동시에 처리하니까). 그게 NPU가 존재하는 이유다.

### 한 문장 요약

**"병목은 우리 코드가 625번의 곱셈을 하나씩 순서대로 처리한다는 점입니다. NPU는 이 반복 연산 자체를 회로로 병렬화해서, 순차 실행의 병목을 근본적으로 없앱니다."**
