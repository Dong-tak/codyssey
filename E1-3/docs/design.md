# 과제 3 — Mini NPU Simulator 기획문서

## 0. 한 줄 요약

2차원 배열 두 개를 겹쳐 같은 위치끼리 곱하고 모두 더하는 **MAC 연산**으로 패턴이 Cross인지 X인지 판별하고, 크기별 연산 시간을 측정해 **O(N²)** 를 실측으로 보이는 콘솔 프로그램.

---

## 1. 핵심 개념 정리

### MAC (Multiply-Accumulate)

```
점수 = Σ (패턴[i][j] × 필터[i][j])
```

같은 위치의 값을 곱해서 전부 더한다. **패턴이 필터와 닮을수록 점수가 커진다.**

- 1이 겹치는 자리 → `1×1 = 1` (점수 상승)
- 1과 0이 만나는 자리 → `1×0 = 0` (기여 없음)

### 판별 원리

Cross 필터 점수와 X 필터 점수를 **비교**해서 더 높은 쪽으로 판정한다. 절대값이 아니라 **상대 비교**라는 점이 중요하다.

### AI에서 왜 중요한가

3×3 필터는 곱셈 9번이면 끝나지만, 실제 모델은 수백×수백 필터를 수천 개 쓴다. 연산 횟수가 **N²에 비례해 폭증**하므로, 이 단순 반복 연산만 병렬로 처리하는 전용 칩(NPU)이 필요해졌다.

## 2. 설계 결정 사항

### D1. 파일 구조 ⚠️ 결정 필요

제출물 명세는 `main.py` + `README.md` 두 개만 언급한다. "main.py: **메인** 실행 파일"이라는 표현은 보조 파일을 허용하는 것으로 읽히지만, 명시적이지 않다.

| 안 | 구성 | 장점 | 단점 |
|---|---|---|---|
| **A. 단일 파일** | `main.py` 하나 | 제출물 명세와 100% 일치. 채점자가 파일 하나만 보면 됨 | 300줄 내외로 길어짐 |
| **B. 모듈 분리** | `main.py` + `mac.py` + `report.py` 등 | 역할이 명확, 과제 2와 일관 | 명세에 없는 파일이 생김 |

> **권장: A안(단일 파일).** 과제 2와 달리 이번 과제는 **클래스 요구가 없고** 제출물이 `main.py`로 못박혀 있다. 함수 단위로만 잘 쪼개면 "기능별 분리" 요건은 충족된다.

### D2. 라벨 정규화 매핑

입력마다 표기가 다르다. **내부에서는 `Cross` / `X` 두 가지만** 쓴다.

| 출처 | 원본 값 | 표준 라벨 |
|---|---|---|
| `patterns[].expected` | `'+'` | `Cross` |
| `patterns[].expected` | `'x'` | `X` |
| `filters[].키` | `'cross'` | `Cross` |
| `filters[].키` | `'x'` | `X` |

**왜 필요한가**: 같은 개념을 `+`, `cross`, `Cross` 세 가지로 부르면 비교할 때마다 조건문이 늘어나고 버그가 생긴다. **경계에서 한 번 변환하고, 내부는 한 가지 표기만** 쓰는 것이 원칙이다.

### D3. 점수 비교 정책 (epsilon)

```
if abs(score_cross - score_x) < 1e-9:
    판정 = UNDECIDED
elif score_cross > score_x:
    판정 = Cross
else:
    판정 = X
```

**왜 필요한가**: `data.json`의 값이 전부 실수(float)다. 수학적으로 같아야 할 두 값이 계산 순서 때문에 `0.9000000000000001` vs `0.8999999999999999` 처럼 미세하게 어긋난다. 단순 `>` 비교를 쓰면 이 **1e-16 수준의 잡음이 판정을 좌우**한다. epsilon은 "이 정도 차이는 같은 것으로 본다"는 선언이다.

### D4. 성능 측정 방법

| 항목 | 결정 |
|---|---|
| 타이머 | `time.perf_counter()` — 단조 증가, 고해상도 |
| 반복 | 크기별 **10회 이상**, 평균 사용 |
| 측정 구간 | **MAC 함수 호출 직전 ~ 직후만**. 파일 읽기·print 제외 |
| 단위 | ms (`(끝 - 시작) * 1000`) |

**왜 반복하나**: 1회 측정은 OS 스케줄링·캐시 상태에 따라 크게 흔들린다. 평균을 내야 N²와의 관계가 드러난다.

### D5. 예외 처리 배치

| 상황 | 처리 위치 | 동작 |
|---|---|---|
| 행/열 개수 불일치 (모드1) | 입력 파싱 함수 | 안내 후 **재입력** |
| 숫자 파싱 실패 (모드1) | 입력 파싱 함수 | 안내 후 **재입력** |
| `data.json` 없음 | 파일 로드 | 안내 후 모드 선택으로 복귀 |
| JSON 문법 오류 | 파일 로드 | 안내 후 복귀 |
| 필터/패턴 크기 불일치 | 케이스 처리 루프 | 해당 케이스만 **FAIL**, 다음 케이스 계속 |
| 알 수 없는 라벨 | 정규화 함수 | 해당 케이스만 FAIL |

**핵심 원칙**: 모드 2는 **한 케이스가 실패해도 전체가 멈추면 안 된다.** 케이스 루프 안에서 `try/except`로 감싸고, 실패 사유를 기록한 뒤 다음으로 넘어간다.

## 3. 컴포넌트 설계

### 함수 목록 (단일 파일 기준)

| 구분 | 함수 | 역할 |
|---|---|---|
| **연산** | `mac(pattern, filter)` | 위치별 곱셈 후 합산 → float 반환 |
| **판정** | `decide(score_cross, score_x, eps)` | `Cross` / `X` / `UNDECIDED` 반환 |
| **정규화** | `normalize_label(raw)` | `'+'`,`'x'`,`'cross'` → `Cross`/`X` |
| **입력** | `read_matrix(name, n)` | n줄 입력받아 2차원 리스트 반환 (검증·재입력 포함) |
| **입력** | `parse_row(line, n)` | 한 줄을 float 리스트로 변환, 실패 시 예외 |
| **로드** | `load_data(path)` | JSON 읽기 + 최상위 스키마 확인 |
| **검증** | `extract_size(key)` | `size_13_2` → `13` |
| **검증** | `check_size(pattern, filter)` | 크기 일치 여부 |
| **성능** | `measure(pattern, filter, repeat)` | 반복 측정 후 평균 ms 반환 |
| **성능** | `make_pattern(n, kind)` | N×N Cross/X 생성 (성능측정·보너스 공용) |
| **출력** | `print_case_result(...)` | 케이스별 점수·판정·PASS/FAIL |
| **출력** | `print_perf_table(rows)` | 크기/시간/N² 표 |
| **출력** | `print_summary(results)` | 총/통과/실패 + 실패 목록 |
| **흐름** | `run_mode1()` | 사용자 입력 모드 |
| **흐름** | `run_mode2()` | JSON 분석 모드 |
| **흐름** | `main()` | 모드 선택 루프 |

> `make_pattern`을 미리 만들어두면 **성능 분석(3×3~25×25 데이터 필요)과 보너스 C2(패턴 생성기)를 동시에 해결**한다. 성능 측정용 데이터를 손으로 만들 필요가 없어진다.

## 4. 데이터 흐름

### 모드 1 (사용자 입력)

```
모드 선택
  → read_matrix("필터 A", 3)   ─ 검증 실패 시 재입력
  → read_matrix("필터 B", 3)
  → 저장 확인 출력
  → read_matrix("패턴", 3)
  → mac(패턴, A) / mac(패턴, B)
  → decide(...)  →  A / B / 판정 불가
  → measure(3×3, repeat=10)  →  평균 ms 출력
```

### 모드 2 (data.json 분석)

```
load_data("data.json")
  → filters 정규화 (cross→Cross, x→X)
  → 로드 완료 메시지 (size_5 / size_13 / size_25)
  → for 각 패턴:
       ├ extract_size(키)  →  N
       ├ 해당 size_N 필터 선택
       ├ check_size()  ─ 불일치 → FAIL 기록 후 continue
       ├ mac × 2 (Cross, X)
       ├ decide()  →  판정
       ├ normalize_label(expected)
       └ 판정 == expected ? PASS : FAIL  →  결과 누적
  → 성능 분석 (3, 5, 13, 25)
  → print_summary()
```

## 5. 예상 결과와 리포트 방향

`data.json` 을 실제로 계산해본 결과다.

| 케이스 | Cross | X | 차이 | 판정 | expected | 결과 |
|---|---|---|---|---|---|---|
| size_5_1 | 0.9 | 0.9 | 1.11e-16 | UNDECIDED | X | **FAIL** |
| size_5_2 | 8.9 | 0.1 | 8.80 | Cross | Cross | PASS |
| size_13_1 | 0.3 | 14.7 | 14.4 | X | X | PASS |
| size_13_2 | 7.5 | 7.5 | 2.66e-15 | UNDECIDED | Cross | **FAIL** |
| size_25_1 | 4.9 | 4.9 | 1.78e-15 | UNDECIDED | X | **FAIL** |
| size_25_2 | 52.9 | 0.1 | 52.8 | Cross | Cross | PASS |

**총 6 / 통과 3 / 실패 3**

### README "결과 리포트"에 쓸 내용

이 3개의 FAIL은 **버그가 아니다.** 세 케이스 모두 두 필터에 대한 MAC 점수가 수학적으로 같고, 남은 차이는 부동소수점 누적 오차(1e-15 수준)뿐이다. 즉 **데이터 자체가 두 필터와 동등하게 닮은 애매한 패턴**이다.

핵심 논지 세 가지:

1. **epsilon이 없었다면** 1e-16짜리 오차의 부호가 판정을 결정한다. 실행 환경이나 합산 순서가 바뀌면 결과가 뒤집힐 수 있는, 신뢰할 수 없는 판정이 된다.
2. **epsilon이 있으면** "구분 불가"를 정직하게 UNDECIDED로 보고한다. expected와 다르니 FAIL이지만, 이것은 **틀린 답을 낸 것이 아니라 답할 수 없음을 밝힌 것**이다.
3. 실무적으로는 이 지점에서 **동점 처리 정책을 정해야 한다** — 재측정, 보조 필터 도입, 또는 사람에게 위임.

### 실패 원인 3분류 (과제 목표 항목)

| 분류 | 이번 과제에서 |
|---|---|
| 데이터/스키마 문제 | 없음 — 크기·키 모두 정상 |
| 로직 문제 | 없음 — MAC·판정 로직 정상 |
| **수치 비교 문제** | **3건 — 동점으로 인한 UNDECIDED** |

## 6. 함정 목록

구현 중 걸리기 쉬운 지점들이다.

| # | 함정 | 대응 |
|---|---|---|
| 1 | `expected`는 `+`/`x`인데 필터 키는 `cross`/`x` → **매핑이 서로 다름** | 정규화 함수 하나로 둘 다 처리 |
| 2 | 모든 값이 float → `==` 비교가 위험 | epsilon 정책 |
| 3 | 패턴 키 `size_13_2` 에서 N 추출 시 `split('_')[1]` | 인덱스 실수 주의, 문자열→정수 변환 필요 |
| 4 | 시간 측정에 `print`나 파일 읽기가 섞이면 **N² 관계가 안 보임** | 측정 구간을 MAC 호출만으로 한정 |
| 5 | 3×3 성능 측정용 데이터가 `data.json`에 없음 | `make_pattern(3, ...)` 로 생성 |
| 6 | 모드 2에서 한 케이스 예외가 전체를 중단 | 케이스 루프 안에서 try/except |
| 7 | 25×25도 연산이 625회뿐이라 **너무 빨라 0.000ms로 보일 수 있음** | 반복 횟수를 늘리거나 소수점 자리수 확보 |
