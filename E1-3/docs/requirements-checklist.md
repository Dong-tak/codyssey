## B. 기능 요구사항 (10개)

### B1. 데이터 구조
- [ ] n×n 2차원 패턴/필터를 저장할 수 있다
- [ ] 특정 위치의 값을 저장·읽기 할 수 있다
- [ ] 3×3, 5×5, 13×13, 25×25 를 모두 처리한다

### B2. 모드 1 입력 처리 (3×3)
- [ ] 필터 A를 "한 줄씩(공백 구분)" 3줄 입력받아 저장
- [ ] 필터 B를 같은 방식으로 입력받아 저장
- [ ] 패턴을 같은 방식으로 입력받아 저장
- [ ] **행 수 불일치** 시 안내 후 재입력 유도
- [ ] **열 수 불일치** 시 안내 후 재입력 유도
- [ ] **숫자 파싱 실패** 시 안내 후 재입력 유도
- [ ] 안내 문구 예: `입력 형식 오류: 각 줄에 3개의 숫자를 공백으로 구분해 입력하세요.`

### B3. 모드 2 JSON 로드 및 스키마 검증
- [ ] `filters` 에서 `size_5`, `size_13`, `size_25` 를 읽는다
- [ ] `patterns` 에서 `size_{N}_{idx}` 키와 `input`(2차원), `expected` 를 읽는다
- [ ] **패턴 키에서 N을 추출**해 해당 `size_N` 필터를 선택한다
- [ ] 필터와 패턴의 **크기 일치를 검증**한다
- [ ] 불일치 시 해당 케이스만 FAIL 처리하고 **원인 메시지를 남긴다**
- [ ] **프로그램이 비정상 종료되지 않는다**

### B4. 라벨 정규화 (필수)
- [ ] 내부 표준 라벨은 `Cross`, `X` 두 가지만 사용
- [ ] `expected` 정규화: `'+'` → `Cross`, `'x'` → `X`
- [ ] `filter` 키 정규화: `'cross'` → `Cross`, `'x'` → `X`
- [ ] 콘솔 출력이 표준 라벨 기준
- [ ] PASS/FAIL 비교가 표준 라벨 기준

### B5. MAC 연산
- [ ] 위치별 곱셈 후 전체 합산을 구현
- [ ] **외부 라이브러리 금지** (NumPy 등) — 반복문으로 직접 구현
- [ ] 결과를 반환 (float 가능)

### B6. 점수 비교 정책
- [ ] 허용오차(epsilon) 기반 비교 적용
- [ ] 기준: `abs(score_a - score_b) < 1e-9` 이면 동점으로 간주

### B7. 판정 및 PASS/FAIL 출력
- [ ] 두 점수 비교 후 A 또는 B로 판정
- [ ] 동점이면 `UNDECIDED`
- [ ] 각 패턴마다 **Cross 점수 / X 점수 / 판정**을 출력
- [ ] 판정이 expected와 같으면 `PASS`, 다르면 `FAIL` 출력

### B8. 성능 분석
- [ ] MAC 연산 시간을 **ms 단위**로 측정
- [ ] 크기별 **10회 이상 반복** 후 평균 출력
- [ ] I/O(입력·출력·파일 읽기) 시간을 제외하고 **연산 함수 호출 구간** 측정
- [ ] 표에 **크기(N×N) / 평균 시간(ms) / 연산 횟수(N²)** 포함

### B9. 결과 리포트
**콘솔**
- [ ] 전체 테스트 수 / 통과 수 / 실패 수 출력
- [ ] 실패 케이스의 **식별자 + 사유 요약** 출력

**README**
- [ ] "결과 리포트" 섹션에 실패 원인 분석 + 시간 복잡도 분석을 **10줄 이상** 서술
- [ ] 실패 0개인 경우에도 "왜 0이 되었는지(정규화/epsilon 정책)" 요약

### B10. 실행 흐름
- [ ] 실행 시 **모드 선택** (1: 사용자 입력 / 2: data.json 분석)
- [ ] 모드 1 순서: 필터 A → 필터 B → 저장 확인 → 패턴 → MAC → 판정 → 성능(3×3)
- [ ] 모드 2 순서: 필터 로드 → 패턴 로드/검증 → MAC/판정/PASS-FAIL → 성능(3×3, 5×5, 13×13, 25×25) → 결과 요약

## G. 사전 확인된 사실 (data.json 실측)

실제 `data.json` 을 분석한 결과다. 구현 전에 알고 있어야 할 내용.

### 구조
```
data.json
├── meta      : version, type
├── filters   : size_5 / size_13 / size_25   각각 { "cross": [[...]], "x": [[...]] }
└── patterns  : size_5_1, size_5_2, size_13_1, size_13_2, size_25_1, size_25_2
                각각 { "input": [[...]], "expected": "+" 또는 "x" }
```

### 실측 결과
- 총 패턴 **6개** (5×5 2개, 13×13 2개, 25×25 2개)
- 모든 값이 **float** (정수 아님) → 부동소수점 비교가 반드시 필요
- 필터 키는 `cross` / `x`, expected 값은 `+` / `x` → **정규화 대상이 서로 다름**
- 크기 불일치 케이스는 **없음** (모든 패턴이 필터와 크기 일치)

### 예상 판정 결과 (epsilon = 1e-9 적용 시)

| 케이스 | Cross 점수 | X 점수 | 점수 차이 | 판정 | expected | 결과 |
|---|---|---|---|---|---|---|
| size_5_1 | 0.900000 | 0.900000 | 1.11e-16 | UNDECIDED | X | **FAIL** |
| size_5_2 | 8.900000 | 0.100000 | 8.80e+00 | Cross | Cross | PASS |
| size_13_1 | 0.300000 | 14.700000 | 1.44e+01 | X | X | PASS |
| size_13_2 | 7.500000 | 7.500000 | 2.66e-15 | UNDECIDED | Cross | **FAIL** |
| size_25_1 | 4.900000 | 4.900000 | 1.78e-15 | UNDECIDED | X | **FAIL** |
| size_25_2 | 52.900000 | 0.100000 | 5.28e+01 | Cross | Cross | PASS |

**총 6개 / 통과 3개 / 실패 3개**

> **이 3개의 FAIL은 버그가 아니라 과제가 의도한 결과다.**
> 세 케이스 모두 두 필터에 대한 MAC 점수가 **수학적으로 동일**하고,
> 남은 차이(1e-15 수준)는 부동소수점 누적 오차일 뿐이다.
> epsilon 정책이 없으면 이 오차의 부호에 따라 판정이 **무작위로** 결정된다.
> README "결과 리포트" 섹션의 핵심 소재가 바로 이 부분이다.
