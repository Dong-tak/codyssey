# 기존 설계와 대조해서 발견한 것

## 1. mode1과 mode2의 판정 라벨이 다르다 (이미 main.py에 반영되어 있었음)

| | mode1 | mode2 |
|---|---|---|
| 판정 라벨 | `A` / `B` / **판정 불가** | `Cross` / `X` / **UNDECIDED** |
| expected 비교 | 없음 (사용자가 그 자리에서 입력한 값이라 정답 자체가 없음) | 있음 → PASS/FAIL 판정 |
| 동점의 결과 | 그냥 "판정 불가"라고 보여주고 끝 | UNDECIDED는 어떤 expected와도 같을 수 없으므로 **항상 FAIL로 집계** |

→ **항목3의 "왜 다르게 뒀는가" 질문의 답**: mode1은 정답(expected)이 없는 즉석 비교이므로 "판정 불가"는 결과 표시일 뿐이고, mode2는 정답이 있는 검증이므로 판정 불가 자체가 "틀렸다(FAIL)"고 명확히 채점되어야 한다. 두 모드의 **목적이 다르기** 때문에 동점을 다루는 의미도 다르다.

## 2. normalize_label을 딕셔너리 매핑으로 만들어야 하는 이유가 명확해짐

항목4의 "새 라벨 `'o'`가 추가되면?" 질문에 좋은 답을 하려면, `if/elif` 사슬이 아니라 **딕셔너리로 확장 가능하게** 설계하는 게 유리하다.

```python
LABEL_MAP = {
    "+": "Cross", "x": "X",
    "cross": "Cross",
}
```

이렇게 하면 "새 라벨이 추가되면 `LABEL_MAP`에 한 줄만 추가하면 된다"고 바로 답할 수 있다. `if/elif`로 짜면 "조건문 하나 더 추가"라고 답해야 해서 덜 깔끔하다.
