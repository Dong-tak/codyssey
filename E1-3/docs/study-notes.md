# 필수 1. 2차원 리스트

## 왜 필요한가
과제 2는 `["A", "B", "C", "D"]` 같은 **1차원** 리스트만 썼다. 이번엔 격자(grid)를 다뤄야 한다.

## 핵심

```python
grid = [
    [0, 1, 0],
    [1, 1, 1],
    [0, 1, 0],
]
```

**리스트를 담고 있는 리스트**다. `grid[1]` 은 `[1, 1, 1]` (두 번째 **행**), `grid[1][2]` 는 `1` (두 번째 행의 세 번째 값).

| 표현 | 의미 |
|---|---|
| `len(grid)` | 행 개수 |
| `len(grid[0])` | 열 개수 (첫 행의 길이) |
| `grid[i][j]` | i행 j열의 값 |

**항상 `[행][열]` 순서**다. 좌표 `(x, y)` 습관 때문에 뒤집어 쓰는 실수가 잦다.

## 이중 for 문

모든 칸을 방문하려면 for를 두 겹으로 쓴다.

```python
for i in range(len(grid)):          # 행
    for j in range(len(grid[i])):   # 열
        print(grid[i][j])
```

바깥 루프가 한 번 돌 때 안쪽 루프가 전부 돈다. → **총 방문 횟수 = 행 × 열 = N²** (필수 4번의 근거)

## ⚠️ 함정: 2차원 리스트 생성

```python
grid = [[0] * 3] * 3      # 위험!
grid[0][0] = 9
print(grid)               # [[9,0,0],[9,0,0],[9,0,0]]  ← 전부 바뀜
```

`* 3` 은 **같은 리스트 3개를 참조**로 복사한다. 올바른 방법:

```python
grid = [[0] * 3 for _ in range(3)]   # 각 행이 독립된 리스트
```

## 직접 확인

```bash

bad = [[0]*3]*3
bad[0][0] = 9
print('잘못된 방법:', bad)

good = [[0]*3 for _ in range(3)]
good[0][0] = 9
print('올바른 방법:', good)
"
```

# 필수 2. 부동소수점 오차 ★ 이번 과제의 핵심

> 과제 목표: "부동소수점 오차가 판정에 어떤 영향을 주는지, 허용오차(epsilon) 기반 비교 정책이 필요한 이유를 설명할 수 있다."

## 왜 필요한가
`data.json` 의 **모든 값이 실수(float)** 다. 그리고 6개 케이스 중 **3개가 이 문제 때문에 FAIL** 난다. 이 개념을 이해 못 하면 README 리포트를 쓸 수 없다.

## 핵심: 컴퓨터는 0.1을 정확히 저장하지 못한다

컴퓨터는 2진수를 쓴다. 10진수 `0.1` 은 2진수로 바꾸면 **무한소수**가 된다(10진수에서 1/3 = 0.333... 인 것과 같은 이치). 저장 공간은 유한하므로 **어딘가에서 잘린다.** 그 잘린 오차가 계산을 거치며 누적된다.

```python
0.1 + 0.2 == 0.3     # False !
0.1 + 0.2            # 0.30000000000000004
```

## 더 중요한 것: 더하는 순서가 결과를 바꾼다

```python
0.1 + 0.2 + 0.3      # 0.6000000000000001
0.3 + 0.2 + 0.1      # 0.6
```

수학적으로는 같아야 하는데 다르다. **MAC 연산은 곱셈 결과를 계속 더하는 작업**이므로, 이 오차가 그대로 누적된다.

## 실제 과제 케이스 재현

`size_5_1` 의 Cross 점수와 X 점수는 **수학적으로 둘 다 0.9** 인데, 실제로는:

```
Cross = 0.9
X     = 0.8999999999999999
차이   = 1.11e-16
```

```bash
python3 -c "
vals = [0.1] * 9
s1 = sum(vals)
s2 = 0.0
for v in reversed(vals):
    s2 += v
print('합계1:', repr(s1))
print('합계2:', repr(s2))
print('차이 :', abs(s1 - s2))
"
```

→ `1.1102230246251565e-16` — 과제의 `size_5_1` 케이스와 **정확히 같은 값**이다.

## 해결책: epsilon 비교

```python
EPSILON = 1e-9

if abs(a - b) < EPSILON:
    # 이 정도 차이는 "같다"고 본다
    판정 = "UNDECIDED"
elif a > b:
    판정 = "Cross"
else:
    판정 = "X"
```

`1e-9` = 0.000000001. 실제 의미 있는 차이(0.1 이상)보다는 훨씬 작고, 부동소수점 잡음(1e-16)보다는 훨씬 크다. **그 사이 어딘가**를 기준선으로 잡는 것이다.

## epsilon이 없으면 무슨 일이 생기나

`a > b` 로만 비교하면, **1e-16짜리 잡음의 부호가 판정을 결정**한다. 합산 순서가 바뀌거나 다른 컴퓨터에서 돌리면 결과가 뒤집힐 수 있다. → **재현 불가능한 프로그램**

## 자가진단
- `0.1 + 0.2 == 0.3` 이 False인 이유를 2진수로 설명할 수 있는가?
- epsilon을 `1e-20` 으로 잡으면 왜 안 되는가? (힌트: 잡음보다 작음)
- epsilon을 `1.0` 으로 잡으면 왜 안 되는가? (힌트: 진짜 차이도 무시됨)

# 필수 3. 시간 측정

## 왜 필요한가
과제 요구사항 B8: "크기별 MAC 연산 시간을 ms 단위로, 10회 이상 반복 후 평균"

## 핵심: `time.perf_counter()` 를 쓴다

```python
import time

start = time.perf_counter()
mac(pattern, filter)              # 측정할 것만
elapsed = time.perf_counter() - start

print(f"{elapsed * 1000:.6f} ms")  # 초 → 밀리초
```

| 함수 | 특징 |
|---|---|
| `time.time()` | 실제 시각. 시스템 시계가 바뀌면 값이 튄다 |
| **`time.perf_counter()`** | **경과 시간 전용. 단조 증가, 고해상도** ← 이걸 쓴다 |

반환값은 **초 단위**이므로 `× 1000` 해야 ms가 된다.

## 왜 10회 평균인가

1회 측정은 심하게 흔들린다. 같은 코드를 3번 재면:

```
1회 측정 1: 0.006417 ms
1회 측정 2: 0.002083 ms
1회 측정 3: 0.001583 ms      ← 4배 차이!
```

OS가 다른 프로그램에 CPU를 넘기거나, 캐시 상태가 다르기 때문이다. **평균을 내야 크기와 시간의 관계가 드러난다.**

## 측정 구간 규칙

```python
# 나쁜 예 — 파일 읽기와 출력이 섞임
start = time.perf_counter()
data = json.load(f)        # I/O
score = mac(p, f)
print(score)               # I/O
elapsed = ...

# 좋은 예 — 연산만
data = json.load(f)
start = time.perf_counter()
score = mac(p, f)
elapsed = time.perf_counter() - start
print(score)
```

I/O가 섞이면 그 시간이 연산 시간을 압도해서 **N²관계가 안 보인다.**

## 직접 확인

```bash

import time
start = time.perf_counter()
total = 0
for i in range(1000000):
    total += i
print(f'{(time.perf_counter()-start)*1000:.3f} ms')
"
```

# 필수 4. 시간 복잡도 O(N²)

> 과제 목표: "크기별 연산 시간을 측정하고, 패턴 크기 증가에 따른 시간 복잡도 O(N²)를 근거와 함께 설명할 수 있다."

## 왜 N²인가

N×N 격자의 **모든 칸**을 한 번씩 방문한다. 칸의 개수가 N×N = N²개이므로, 연산 횟수도 N²에 비례한다.

| 크기 | 연산 횟수 | 3×3 대비 |
|---|---|---|
| 3×3 | 9 | 1배 |
| 5×5 | 25 | 2.8배 |
| 13×13 | 169 | 18.8배 |
| 25×25 | 625 | **69.4배** |

**N이 8배(3→25) 커지면 연산은 69배** 늘어난다. 이것이 "AI 연산량이 기하급수적으로 늘어난다"는 말의 의미다.

## 실측 결과

```
크기      평균(ms)     연산수    이전 대비
3×3      0.000812      9       -
5×5      0.001446     25      1.8배
13×13    0.006821    169      4.7배
25×25    0.023175    625      3.4배
```

## ⚠️ 측정값이 이론과 정확히 안 맞는 이유

연산 횟수는 9→25 로 2.8배인데 시간은 1.8배다. 왜?

작은 크기에서는 **함수 호출·루프 준비 같은 고정 비용(오버헤드)이 상대적으로 크기** 때문이다. 크기가 커질수록 순수 연산 비중이 늘어 이론값에 가까워진다.

**README에는 이 점을 함께 써야 한다.** "측정값이 정확히 N²는 아니지만, 크기가 커질수록 N² 경향에 수렴한다"가 정확한 서술이다.

- 100×100은 3×3의 몇 배인가? (답: 10000/9 ≈ 1111배)
- 왜 작은 크기에서 이론과 어긋나는가?

# 보조 5. 문자열 파싱

## 왜 필요한가
모드 1에서 `"0 1 0"` 같은 한 줄을 받아 `[0.0, 1.0, 0.0]` 으로 바꿔야 한다.

## 핵심

```python
line = " 0 1 0 "
parts = line.split()          # ['0', '1', '0']  ← 공백 여러 개도 알아서 처리

```

`split()` 을 인자 없이 쓰면 **앞뒤 공백 제거 + 연속 공백 무시**가 자동이다. `split(" ")` 와 다르다.

```python
" 0  1 ".split()      # ['0', '1']       ← 깔끔
" 0  1 ".split(" ")   # ['', '0', '', '1', '']  ← 빈 문자열 섞임
```

## 검증 두 가지

```python
if len(parts) != n:
    raise ValueError(f"{n}개의 숫자가 필요합니다")

try:
    values = [float(p) for p in parts]
except ValueError:
    print("숫자가 아닌 값이 있습니다")
```

`float("abc")` 는 `ValueError` 를 낸다. 과제 2의 `int(raw)` 처리와 같은 패턴이다.

## 자가진단

# 보조 7. MAC 연산 (도메인 개념)

> 과제 목표: "MAC 연산이 무엇이고, AI에서 왜 중요한지 설명할 수 있다."

## 정의

**Multiply-Accumulate** — 곱하고(Multiply) 누적해서 더한다(Accumulate).

```
점수 = Σ (패턴[i][j] × 필터[i][j])
```

## 왜 이게 "닮음"을 재는가

| 상황 | 곱셈 결과 | 의미 |
|---|---|---|
| 1 × 1 | 1 | 둘 다 켜짐 → **점수 상승** |
| 1 × 0 | 0 | 한쪽만 켜짐 → 기여 없음 |
| 0 × 0 | 0 | 둘 다 꺼짐 → 기여 없음 |

**겹치는 칸이 많을수록 총점이 커진다.** 그래서 총점이 곧 유사도다.

## 판정은 상대 비교

절대 점수로 판단하지 않는다. **Cross 필터 점수와 X 필터 점수를 비교**해서 높은 쪽으로 정한다. 어떤 패턴의 Cross 점수가 5점이어도, X 점수가 7점이면 X로 판정한다.

## AI에서 왜 중요한가

- 3×3 필터: 곱셈 9번
- 실제 AI 모델: 수백×수백 필터 × 수천 개 → **한 장 처리에 수억 번**
- CPU는 복잡한 명령을 **순서대로** 처리하도록 설계됨 → 단순 반복에 비효율
- → **단순 곱셈-덧셈만 동시에 수천 개** 처리하는 전용 칩 = **NPU**

## 자가진단
- 3×3 십자가 패턴 × 십자가 필터 = 몇 점인가? (답: 5)
- 왜 CPU 대신 NPU가 필요한가?
